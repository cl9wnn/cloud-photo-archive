# cloudphoto — фотоархив в Yandex Object Storage

`cloudphoto` — приложение командной строки для управления фотоальбомами и публикации статического сайта в Yandex Object Storage.

Адрес сайта проекта: [https://photos.vvot27.itiscl.ru/](https://photos.vvot27.itiscl.ru/).

Программа запускается локально в Linux. Фотографии и HTML-страницы хранятся в Object Storage. DNS-запись связывает домен с бакетом, а сертификат из Certificate Manager обеспечивает HTTPS. Отдельный сервер для сайта не требуется.

## 1. Возможности

| Команда | Назначение |
|---|---|
| `list` | Вывести список альбомов или фотографий выбранного альбома |
| `upload` | Отправить фотографии из локального каталога в альбом |
| `download` | Скачать фотографии альбома в локальный каталог |
| `delete` | Удалить фотографию или весь альбом |
| `mksite` | Сформировать и опубликовать HTML-страницы фотоархива |

Фотографиями считаются файлы с расширениями `.jpg` и `.jpeg` без учёта регистра расширения. Имена сохраняются с исходным регистром: `Photo.JPG` и `photo.jpg` — разные фотографии.

## 2. Требования к окружению

Для приложения:

- Linux на архитектуре x86_64; для проекта используется Ubuntu Desktop в VirtualBox.
- Python 3.10 или новее, `pip` и модуль `venv`.
- Доступ к интернету и API Yandex Object Storage.
- Существующий бакет и статический ключ сервисного аккаунта с необходимыми правами.

Зависимость приложения — `boto3==1.43.123`. Она устанавливается автоматически из `pyproject.toml`.

Для первоначального создания инфраструктуры:

- Terraform версии `>= 1.5, < 2.0`.
- Провайдер `yandex-cloud/yandex` версии `0.243.0` — загружается при `terraform init`.
- Установленный и настроенный Yandex Cloud CLI (`yc`).
- Каталог Yandex Cloud, публичная DNS-зона `vvot27.itiscl.ru` и выпущенный сертификат для `vvot27.itiscl.ru` и `*.vvot27.itiscl.ru`.
- У аккаунта Terraform должны быть права на создание ресурсов, назначение роли сервисному аккаунту, изменение DNS-записей и использование сертификата.

Рабочий каталог желательно размещать внутри файловой системы Ubuntu. Для проверки файлов, различающихся регистром, общая папка Windows может не подойти.

## 4. Сборка и установка приложения

Все следующие команды выполняются из корневого каталога проекта — папки, содержащей `cloudphoto.py` и `pyproject.toml`.

### Подготовка Ubuntu

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip

uname -m
python3 --version
```

Ожидаемая архитектура — `x86_64`, версия Python — не ниже 3.10.

### Установка в виртуальное окружение

```bash
python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade pip
python -m pip install -e .
```

`pip` устанавливает зависимости и создаёт команду `.venv/bin/cloudphoto`. Параметр `-e` включает режим разработки: изменения исходника доступны без переустановки пакета. Отдельная компиляция программы в бинарный файл не требуется.

В новом терминале активируйте окружение заново:

```bash
source .venv/bin/activate
```

Если нужен установочный пакет wheel:

```bash
python -m pip wheel --no-deps --wheel-dir dist .
```

Результат сборки — файл `dist/cloudphoto-1.0.0-py3-none-any.whl`. Его можно установить в другом виртуальном окружении:

```bash
python -m pip install dist/cloudphoto-1.0.0-py3-none-any.whl
```
## 5. Создание инфраструктуры через Terraform

Этот раздел описывает первоначальное развёртывание. Если инфраструктура уже создана, используйте её существующее состояние Terraform и переходите к настройке приложения. Для управления уже созданными ресурсами нужно сохранить соответствующий `terraform.tfstate`; один исходный код конфигурации не заменяет состояние.

### Входные переменные

```bash
cp terraform/terraform.tfvars.example terraform/terraform.tfvars
```

Заполните `terraform/terraform.tfvars` собственными значениями:

```hcl
folder_id            = "ID_КАТАЛОГА"
bucket_name          = "photos.vvot27.itiscl.ru"
domain               = "vvot27.itiscl.ru"
cert_id              = "ID_СЕРТИФИКАТА"
dns_zone_id          = "photos.vvot27.itiscl.ru"
existing_dns_zone_id = "ID_DNS_ЗОНЫ"
```

| Переменная | Значение |
|---|---|
| `folder_id` | ID каталога, в котором создаются ресурсы |
| `bucket_name` | Имя бакета; совпадает с доменом сайта и переменной `BUCKET` приложения |
| `domain` | Домен существующей DNS-зоны без завершающей точки |
| `cert_id` | ID существующего выпущенного сертификата |
| `dns_zone_id` | Полное доменное имя сайта — согласно буквальному описанию в ТЗ |
| `existing_dns_zone_id` | Настоящий ID существующей DNS-зоны |

**Особенность ТЗ:** переменная с именем `dns_zone_id` описана в задании как доменное имя сайта. В реализации сохранено это описание. Для реального ID зоны, необходимого API, добавлена отдельная переменная `existing_dns_zone_id`.

Конфигурация проверяет соответствие:

```text
bucket_name = dns_zone_id = photos.<domain>
```

Для собственного домена имя бакета должно совпадать с адресом сайта. См. [документацию Object Storage](https://yandex.cloud/ru/docs/storage/operations/hosting/own-domain).

### Аутентификация Terraform

В предварительно настроенном Yandex Cloud CLI получите IAM-токен:

```bash
export YC_TOKEN="$(yc iam create-token)"
```

Провайдер получает токен из `YC_TOKEN`; в файлах Terraform токен не задаётся. При истечении срока его действия повторите команду получения токена.

### Планирование и применение

```bash
export TF_CLI_CONFIG_FILE="$PWD/terraform/provider-mirror.tfrc"

terraform -chdir=terraform init
terraform -chdir=terraform fmt -check
terraform -chdir=terraform validate
terraform -chdir=terraform plan -out=cloudphoto.tfplan
```

Просмотрите план. Для нового развёртывания создаются шесть ресурсов:

1. Сервисный аккаунт приложения.
2. Назначение ему роли `storage.admin` в учебном каталоге.
3. Статический ключ доступа.
4. Бакет с настройками статического сайта и HTTPS.
5. Публичный ACL бакета.
6. CNAME-запись, направляющая домен сайта на `<bucket_name>.website.yandexcloud.net.`.

DNS-зона и сертификат используются существующие.

```bash
terraform -chdir=terraform apply cloudphoto.tfplan
terraform -chdir=terraform state list
terraform -chdir=terraform output website_url
```

Дождитесь сообщения `Apply complete!`. Команда `plan` сама по себе не создаёт ресурсы и статические ключи.

## 6. Переменные окружения приложения

Программа получает параметры подключения только через три переменные:

| Переменная | Назначение |
|---|---|
| `BUCKET` | Имя бакета, например `photos.vvot27.itiscl.ru` |
| `AWS_ACCESS_KEY_ID` | Идентификатор статического ключа сервисного аккаунта |
| `AWS_SECRET_ACCESS_KEY` | Секретная часть статического ключа |

После успешного `terraform apply` можно получить значения из outputs, не выводя ключи на экран:

```bash
BUCKET="$(terraform -chdir=terraform output -raw bucket_name)" &&
AWS_ACCESS_KEY_ID="$(terraform -chdir=terraform output -raw access_key_id)" &&
AWS_SECRET_ACCESS_KEY="$(terraform -chdir=terraform output -raw secret_access_key)" &&
[[ -n "$BUCKET" && -n "$AWS_ACCESS_KEY_ID" && -n "$AWS_SECRET_ACCESS_KEY" ]] &&
export BUCKET AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY
```

Проверьте запуск:

```bash
cloudphoto --help
cloudphoto list
```

Для пустого архива `list` ничего не печатает и возвращает код `0`.

Переменные нужно задавать в каждом новом терминале. IAM-токен `YC_TOKEN` используется Terraform и не требуется самой программе `cloudphoto`.

Конфигурационный файл приложения не используется. Настройка через `aws configure`, `.env` или файлы `~/.aws` не требуется. Регион и endpoint закреплены в коде:

```text
region:   ru-central1
endpoint: https://storage.yandexcloud.net
```

Эти параметры соответствуют [документации boto3 для Yandex Object Storage](https://yandex.cloud/ru/docs/storage/tools/boto).

## 7. Использование

### Список альбомов и фотографий

```bash
cloudphoto list
cloudphoto list --album "Животные"
```

Каждое имя выводится на отдельной строке. Сортировка выполняется по байтам UTF-8 с учётом регистра. Для пустого существующего альбома вывод пустой; отсутствие самого альбома считается ошибкой.

### Загрузка фотографий

```bash
cloudphoto upload --album "Животные" --path ./photos
```

`--path` указывает на **каталог**, а не на отдельный файл. Программа загружает JPEG из этого каталога без обхода вложенных папок. Если альбома нет, он создаётся. Фотография с совпадающим исходным именем в этом альбоме заменяется.

Если `--path` пропущен, используется текущий каталог:

```bash
(
  cd photos
  cloudphoto upload --album "Животные"
)
```

Недоступный каталог или отсутствие фотографий приводят к ошибке. При отсутствии фотографий новый альбом не создаётся.

### Скачивание фотографий

```bash
mkdir -p downloaded
cloudphoto download --album "Животные" --path ./downloaded
```

Каталог назначения нужно создать заранее. Имена файлов сохраняются, существующие одноимённые файлы заменяются. Без `--path` используется текущий каталог.

Передача выполняется во временный файл. Целевой файл заменяется только после успешного скачивания.

### Удаление

Удалить одну фотографию:

```bash
cloudphoto delete --album "Животные" --photo fox.jpeg
```

Удалить альбом и все его фотографии:

```bash
cloudphoto delete --album "Животные"
```

После удаления последней фотографии альбом остаётся пустым. Для удаления самого альбома используется команда без `--photo`. Отсутствие указанного альбома или фотографии приводит к ошибке.

### Публикация сайта

```bash
cloudphoto mksite
```

При каждом запуске команда:

1. Применяет публичное чтение через ACL `public-read`.
2. Настраивает главную страницу `index.html` и страницу ошибки `error.html`.
3. Сортирует альбомы и нумерует их от 1 до N.
4. Создаёт страницы `album1.html`, `album2.html` и далее.
5. Публикует обновлённые `index.html` и `error.html`.
6. Удаляет оставшиеся от прошлой публикации лишние страницы `albumN.html`.

Фотографии при этом повторно не загружаются. Текст и значения HTML-атрибутов экранируются, ссылки кодируются для URL. Для пустого архива и пустого альбома формируются соответствующие страницы.

После `upload` или `delete` вызовите `mksite`, чтобы сайт отразил изменения. Можно сначала выполнить несколько операций, затем один раз обновить сайт.

Для галереи используются Galleria и jQuery по HTTPS-ссылкам из шаблонов ТЗ. Браузеру необходим доступ к соответствующим CDN.

## 8. Схема организации облачного хранилища

Для альбомов и фотографий используется отдельный префикс `albums/`. Имя альбома и исходное имя файла кодируются как шестнадцатеричное представление байтов UTF-8:

```python
encoded = original_name.encode("utf-8").hex()
original_name = bytes.fromhex(encoded).decode("utf-8")
```

Общая структура бакета:

```text
albums/
  <hex имени альбома>/
    marker
    photos/
      <hex исходного имени фотографии>

index.html
error.html
album1.html
album2.html
...
```

Например, альбом `A` и фотография `a.jpg`:

```text
albums/41/marker
albums/41/photos/612e6a7067
```

`marker` — объект с пустым содержимым. Его наличие означает, что альбом существует. Пустой альбом представлен только маркером.

### Обоснование схемы

- **Однозначность.** Ключ фотографии содержит код имени альбома и код исходного имени файла. Кодирование обратимо, поэтому отдельная таблица соответствий не требуется.
- **Сохранение регистра.** `Photo.JPG` и `photo.jpg` кодируются по-разному. Программа не изменяет регистр исходных имён и не выполняет нормализацию Unicode.
- **Специальные символы.** Кириллица, пробелы, кавычки, амперсанды и другие допустимые символы превращаются в ASCII-последовательность. Имена не конфликтуют с разделителями ключа. Пустые имена и имена с `/` отклоняются.
- **Пустые альбомы.** Существование альбома определяется маркером, а не наличием фотографий. Удаление последней фотографии не удаляет маркер.
- **Совпадающие имена.** Фотографии с одинаковыми именами в разных альбомах имеют разные ключи. Повторная загрузка того же имени в тот же альбом заменяет существующий объект.
- **Изоляция страниц.** Фотографии находятся под `albums/`, а служебные HTML-страницы — в корне. Они однозначно различаются.
- **Повторяемость.** Одни и те же имена всегда дают одинаковые ключи. При полном удалении альбома маркер удаляется после его остальных объектов.

Для отображения списка программа декодирует имена и сортирует их по исходным байтам UTF-8. Временная нумерация страниц при `mksite` не влияет на ключи фотографий.

Шестнадцатеричное кодирование увеличивает длину имени вдвое относительно числа байтов UTF-8. Программа проверяет ограничение полного ключа в 1024 байта и отклоняет слишком длинные ключи.

## 9. Проверка результата

Базовый сценарий для каталога `photos` с JPEG-фотографиями:

```bash
cloudphoto upload --album "Проверка" --path ./photos
cloudphoto list
cloudphoto list --album "Проверка"

mkdir -p downloaded
cloudphoto download --album "Проверка" --path ./downloaded

cloudphoto mksite
```

Проверьте сайт в браузере: HTTPS, список альбомов, галерею, названия фотографий и возврат на главную. Несуществующий адрес, например `/missing.html`, должен показывать страницу ошибки.

Дополнительно проверьте замену файлов, удаление отдельной фотографии, сохранение пустого альбома и повторный `mksite`.
